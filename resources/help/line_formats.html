{{const:APP_NAME}} line format reference

How {{const:APP_NAME}} reads the lines your firmware prints: where a line ends, how its level is decided, which numbers are plotted, which columns a CSV log gets, and which lines mark a restart. For version {{const:APP_VERSION}}.

Quick start

Three habits let {{const:APP_NAME}} read your firmware's output with no set-up:

  1. One reading per line, with names. temp: 23.3, hum: 53 plots temp and hum.
  2. The levels your logging framework already prints. E (1234) wifi: timeout is shown as an Error, and so is [ERROR] sensor timeout.
  3. plt: in front of each reading, when readings are mixed with messages. See Marking the reading lines.

End every line with a newline. The rest of this page gives the exact rules.

Lines

  • A line ends at LF (\n), CR LF (\r\n) or a lone CR (\r). A CR LF split across two reads is still one ending.
  • Text is read as UTF-8. A byte that is not valid UTF-8 is shown and logged as \xNN, so its value is kept.
  • Tab is kept. Other control characters are shown and logged as escapes: a bell (byte 07) appears as \x07.
  • ANSI escape codes (colours, cursor moves) are removed from what is shown, logged and exported. Their colours can be shown in the console: switch on ANSI colours on the Features page of Preferences. A line made only of escape codes, such as a clear-screen, is dropped.
  • A line longer than {{count:SERIAL_MAX_LINE_BYTES}} bytes is cut into pieces of that length.

Everything below reads a line after these steps, so a coloured ESP-IDF line is read like a plain one.

Levels

Each line gets one level: Critical, Error, Warning, Info, Debug or Data. The level sets the line's colour and the level buttons above the console. It never decides whether a line is logged, exported or plotted.

A level that a logging framework prints decides the line's level. {{const:APP_NAME}} looks for one in this order:

Plot data

When {{const:APP_NAME}} looks

Once the plot has {{count:PLOT_AUTODETECT_SAMPLE_SIZE}} lines, {{const:APP_NAME}} looks for numbers in all the lines since the plot opened, and again with each new line, until it finds them. A plot opened later starts from the most recent {{count:PLOT_RECENT_LINES_BUFFER_SIZE}} lines. After {{count:PLOT_DETECTION_GIVE_UP_LINES}} lines with no numbers found, the plot says so and offers Describe the format...

Points are placed at the time each line arrived on the computer. Times the device prints are not used.

Three forms, tried in this order

1. JSON, one object per line

{"temp": 22.4, "hum": 55, "ok": true}

Plotted: temp, hum

The line starts with {; spaces before it are allowed. A number, or a string holding a number such as "55", is a value. true and false are not.

2. Names and values

temp: 22.4, hum: 55

Plotted: temp, hum

temp=22.4 hum=55

Plotted: temp, hum

A name is letters, digits, underscores and spaces, up to {{count:STRUCTURE_KEY_MAX_LENGTH}} characters, followed by : or =. The value is a number. Text right after the number is ignored, so temp: 22.4C plots 22.4. Anything else on the line is ignored.

3. Values only

22.4,55,1013

Plotted: ch0, ch1, ch2

Separators are tried in this order: comma, tab, semicolon, bar (|), then spaces. Every field must be a number, and a line needs at least two. The values are named ch0, ch1 and so on, unless they are named with plt!.

How values are chosen

  • A form is used when at least {{percent:STRUCTURE_MIN_MATCHING_FRACTION}} of the lines looked at are in it.
  • A name becomes a value when it is on at least {{percent:STRUCTURE_KEY_FREQUENCY_THRESHOLD}} of those lines, in the order the firmware prints them. Occasional lines without it are fine.
  • For values only, the most common number of fields is used. A line with another number of fields, or with a field that is not a number, is not plotted. It is still shown and logged.
  • At most {{count:PLOT_MAX_SERIES}} values are followed. Lines that carry more give the first {{count:PLOT_MAX_SERIES}}.

Numbers

Write a number with a point as the decimal separator, and an optional sign and exponent: 22, -3.5, 1.2e-3. Write a digit before the point: 0.5, not .5. A decimal comma, as in 3,5, is not read as a number.

Marking the reading lines: plt:

When the firmware prints messages and readings, start each reading line with plt::

I (1001) app: loop 41
plt: 21.1,51

Plotted: ch0, ch1, from the plt: line only

If any line looked at starts with plt:, only the lines that start with it are plotted, and the rest of each such line is read in the three forms above. Letter case does not matter. The prefix may carry digits, as in plt1:, which version {{const:APP_VERSION}} reads the same as plt:.

Naming values: plt!

plt! Temperature,Humidity
plt: 21.1,51

Plotted: Temperature, Humidity

A line that starts with plt! names the values of values-only lines, in order. It is used when it has as many names as the lines have values, and the first such line wins. Print it before the readings, so that it is among the lines {{const:APP_NAME}} looks at. JSON and name and value lines keep their own names.

Any other form: a pattern

View > Configure plot... takes a pattern with named groups, such as RPM:\s*(?P<RPM>\d+). Each named group is a value. Capture from sample... builds the pattern for you: click each number in a recent line and give it a name. The pattern is looked for anywhere in the line, and a group that does not hold a number is skipped on that line. A pattern that takes more than {{const:PLOT_REGEX_TIMEOUT_SECONDS}} s on a line skips that line; after {{count:PLOT_REGEX_MAX_CONSECUTIVE_TIMEOUTS}} such lines in a row, the plot stops and says so. A pattern can be saved as a profile.

CSV logs

A log written as CSV gets its columns from JSON objects or from names and values, found as for the plot, with these differences:

  • A name starts with a letter or an underscore, so a clock time such as 12:30:45 is never read as a name.
  • A value is any text up to a space, a comma or a semicolon.
  • A line becomes a row when it has at least {{percent:CSV_ROW_MIN_COLUMN_FRACTION}} of the columns. Other lines are left out of the CSV and kept in the text log.
  • With no names after {{count:CSV_DETECTION_GIVE_UP_LINES}} lines, the CSV has two columns, Timestamp and Data. Values-only lines are written this way.
  • A value that a spreadsheet would read as a formula is written with a quote in front of it.
temp: 21.1, hum: 51

Columns: Timestamp,temp,hum

Restarts

When a board restarts, {{const:APP_NAME}} adds a notice after the line, such as [{{const:APP_NAME}}] Board restart 2 of this session: POWERON_RESET, to the console, the log and any export, and counts it in Device > Session report... Restart detection can be switched off on the Features page of Preferences.

BoardLineReason given
ESP32, every chip of the familyrst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)
printed by the boot ROM, at the start of a line		The name in brackets: POWERON_RESET
Zephyr*** Booting Zephyr OS build v3.7.0 ***
or *** Using Zephyr OS v3.7.99 ***, at the start of a line		Zephyr boot banner

One restart is counted once. A Zephyr banner that follows an ESP32 reset line, or MCUboot's Jumping to the first image slot, with no banner between, belongs to that restart:

rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)
*** Booting Zephyr OS build v3.7.0 ***

Counted once: POWERON_RESET

A bootloader built on Zephyr whose own log is switched off prints no such line, and its restarts are counted twice.

Examples

Arduino

Serial.print("temp: ");
Serial.print(temperature, 1);
Serial.print(", hum: ");
Serial.println(humidity);

Prints:

temp: 23.3, hum: 53

Plotted: temp, hum

ESP-IDF

ESP_LOGI(TAG, "temp=%.1f hum=%d", temperature, humidity);
ESP_LOGE(TAG, "read failed: %d", err);

Prints:

I (1003) sensor: temp=23.3 hum=53

Plotted: temp, hum

E (1004) sensor: read failed: -1

Error, from the E marker

Zephyr

printk("plt: %d,%d\n", temperature_centi, humidity);

Prints a line with no timestamp in front, so it starts with plt::

plt: 2333,53

Plotted: ch0, ch1

Plain C

printf("{\"temp\": %.1f, \"hum\": %d}\n", temperature, humidity);

Prints:

{"temp": 23.3, "hum": 53}

Plotted: temp, hum

Alternating lines like these are not plotted.

Known issues

Zephyr's default timestamp, as in the line below, is read as a name and a value, so the plot shows an extra value named 00 that is always 0. Untick it in the plot's value list, or print readings with printk("plt: ...") as in the Zephyr example.

[00:00:03.234,000] <inf> sensor: temp: 23 hum: 53

Plotted: 00, temp, hum
